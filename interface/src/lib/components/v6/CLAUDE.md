# V6 UI Components

All Svelte 5 components for the looping interface. Organized by functional area.

## Directory Structure

| Directory | Purpose |
|-----------|---------|
| `browser/` | **DrillDownBrowser** (ADR-391) - One-layer-per-tap preset browser over Live's sidebar Places (Recent + one rail button per Place, a MIDI \| Simpler \| Audio switch, and the scale picker). Has its own CLAUDE.md (component + `utils/` layout: grid solver, grouping and windowing, the loader, the vendor model). |
| `central/` | **CentralDisplay** - Main content area showing device-specific detail views. **Spacing is by role, not size (ADR-434, 2026-09-14):** a view never writes a size for its inset or for the space between controls — it uses `p-(--central-inset)` and `gap-(--central-gap)`, 16px, or 8px under `data-density="compact"`, which a view sets on its root only when its control COUNT comes from what is loaded (Drum Rack, Instrument / Pattern / Audio Effect Rack, Komplete Kontrol) and which anything mounted inside inherits. Spacing inside one control — a chooser's options, a title over its group, a badge — stays the control's own; row components (`SamplerControlsRow` and kin) carry no padding. `npm run shot:tour -- central` fails when a divider's gaps or a view's inset drift from its roles. **Groups in a central view are separated by a hairline, not fenced in a card (ADR-433, 2026-09-13):** `central/SectionDivider.svelte` is a 1px rule, `vertical` or `horizontal`, fading at both ends so it reads as a seam rather than as another box edge, optionally inked with the device it introduces. It carries **no text** — where a group needs a name the name is a centered, upright 0.75rem eyebrow at the top of the group, and most groups need none, since the seam plus the device's own ink already says where the boundary is. A seam in a flex row is just another child; a seam in a grid needs an `auto` track and a renumber of that view's literal `grid-column` table (`ClipCentralView`, `SystemCentralView`, `PermuteCentralView`). This replaced the per-view card idioms — Squash's two `.dyn-panel`s, Drift's three `.drift-card`s, the Bass panel, `EnvelopeCard` (now `EnvelopeGroup`: two hairlines bracketing the stages with "Amp Envelope" upright above them) and the System view's five `.glass-panel-subtle` blocks — because every control here is already a bordered box, so a card was a box of boxes costing ~20px of a 660px band in padding alone. The views that had **no** separator at all (Reverb, the Drum Rack's pads against its controls, the Arpeggiator's four devices, Permute's two sequencers, the Clip rail, the Chorus view's three devices — Smudge | Comb + Comb LFO | Phaser) gained one. A second pass the same day, from a screenshot audit of every reachable view, added the rest: every instrument view seams its pitch/mod wheels off from the device, Pedal seams every device, Drum Buss seams Boom, and Variation, Meld, the Pattern rack, nested-rack kits and Simpler's Random Start each gained one; Tremolo's Random box became a seam; `EnvelopeGroup edges="trailing"` where the group opens the band (Operator). Under the flat grammar every seam draws `--line-strong`, so `ink` has no visible effect in the shipped skin. `AutoFilterCentralView`'s hand-rolled `bg-border/60` rule — the prior art — is now the shared component. **`views/SystemCentralView.svelte` is the MASTER track's view** (selecting track `-1` switches to it). **Since 2026-09-26 it is two groups in the Settings page's grammar — Transport (the three value fields over a Click | Follow Key row) and Sections (Header · FX · Clips, top to bottom as they sit on the flipped screen), each switch a row with an On/Off chip — and a gear in the view's top-right corner opens `settings/SettingsPage.svelte`, a full-page view mounted by `layouts/default/Layout.svelte` (`settingsStore.open`, z-index over the status strip): a sidebar (tabs under 760px) of General (Behavior, Appearance, Foot Switch), Places (grouped, ticked first, Packs folded, a filter; `placesGroups.ts`), Grooves (Live's Core Library groove files, ticked for the Groove view that touching Q opens; `groovesGroups.ts`, `logs/grooves.json`) and Connection (Live, the iPad address from `/api/network`, the features), with Setup ahead of them on a first run, on the same addresses and echoes. VIEW, PADS, FLIP and INST have no switch any more: the central view, the Drum Rack's pad column, the flipped stack and the strips' device band are always on (`uiPrefsStore` answers `true`). What follows is the history of the view.** Before the split it was four full-height columns of named groups (bordered cards until ADR-433): **Transport** (drag-tempo, drag-time-signature, launch-quantization value, Click — the three values sit in bordered fields on one row, Click on a row of the same pitch as the switches beside it, so the whole view reads as one grid of touch rows), **Behavior** (`auto_arm` / `move_volume_knob` / `auto_capture` — the SessionSettings toggles the `owner/menubar` utility also drives, written **echo-confirmed** rather than optimistically because they are surface-side bools with no LOM round trip to answer for them), **Appearance** (theme — the skin chooser was removed 2026-08-31 when Hybrid became the only skin), and **Sections** — the seven "what is on screen" `uiPrefsStore` prefs, ordered the way the things they control appear down the screen: **Header** (top edge) · **Solo** (inside the strips) · **Clips** · **View** · **Pads** (2026-09-08 — the pad column inside the Drum Rack central view, i.e. inside the section **View** switches, which is why it follows it) · **FX** · **Flip** (ADR-421, last because it inverts that very order and cannot be read before it). **Two columns, not one stack** (`.sys-sections-grid`, `grid-auto-flow: column` so it still reads down the left then down the right): six rows sharing the card's ~256px left each one 39px, and no global touch floor catches it (`app.css` sets none since 2026-09-28; the touch floor is each control's own), so a 39px row renders happily at the iPad's 1366px landscape width. Since PADS made seven, the grid is **four rows of two** rather than three: a seventh switch in a 3-row grid opens an implicit THIRD column at ~44px a cell against a ~70px label, so four rows keep two columns and spend the cost on one empty cell at the foot of the second. Measured at 1366x1024: **60.6 x 75.9px a switch** at the default three sections — the same row pitch as Behavior's toggles beside it — and 39px with CLIPS on, where Behavior is also 39px and Transport's Click row 32px; that squeeze belongs to the four-section stack, not to this grid. The labels need `padding-inline: 0.375rem` / `font-size: 0.8125rem` there to fit half a card's width. **PADS is the one row that is not a section**: it takes width off one view, not height off the stack, so it never reaches `visibleSectionCount`. It belongs in this card anyway — it asks the card's question (how much of the screen goes to what), and the pad grid is the only door to per-pad editing, the FX grid's Pitch slider included. **There is no MINI switch** — the mini session column is now simply the complement of CLIPS (`miniSessionActive` = `!sessionMode`), because the only layout its pref could buy was "no clips visible anywhere". Equal weight because none outranks another; reading order = layout order. The three section switches came from `SessionLayoutToggles` (deleted), which had lived in the browser rail and, before that, the right sidebar. Because the card is inside the section **View** switches, View can hide its own control — `MasterTrack.handleSelect` (a master-strip tap, the direct way back), `TrackStrip.selectThen` (a strip's Clip/Permute tap) and `TracksPanelV6.focusSlot` (a long-pressed grid cell) all turn the section back on. Sections has its own grid column rather than a shelf under Appearance: stacked under it, the combined rows fell under the 44px touch floor at three sections. **Remove Silent is gone (2026-09-25)**: the hold-to-delete sweep of silent tracks, its Tracks card, `$lib/utils/emptyTrackCleanup.ts` and the surface's `/looping/v3/track/delete` wire (`TrackCreateComponent`) were removed as too flaky to trust mid-set. Delete tracks in Live. **Launch quantization is a modal**, not a permanent chip row: 14 values spent a whole grid row on a control set once per set, so the current value now reads as a third transport digit and tapping it opens a 7x2 picker. The picker is absolute inside the view's own box, so it dims this section only and the track strips stay readable. The readouts size off container height (`cqh` on `.sys-root`), since the central section is half the screen with the FX grid off and a third with it on. **The swap pill (ADR-439, 2026-09-15):** `central/SwapControl.svelte` — the loaded name between two arrows, where a press on the pill's left half steps back and on its right half forward (two half-width buttons under one centered name, each its own `use:press`, so the split is always the middle); no Commit, no Return and no readout, the user's call the same day — is mounted by `CentralDisplay` **down the LEFT of every instrument view, standing on its end** (the same day, the user's call, after a day as a row above the view): a column `--height-touch` across (44px, the touch floor in its narrow axis) and as tall as the frame's content, the up arrow at the top stepping back and the down arrow at the foot forward — down is the order a catalog folder lists its presets in — with the name between them in `writing-mode: vertical-rl` turned 180° so it reads bottom to top, ellipsised at the reading end when it is longer than the column. **It costs the views width, not height:** the row took 52-60px off a 329px band every view was laid out for the whole of, and the column gives the same back and takes it out of 1062px of width instead. Transparent around the pill, with the mounted view's `data-density` mirrored onto it (a `MutationObserver` on the view host) so its inset is the view's (ADR-434) and the view's own inset beside it is the gap. **A view can place the pill itself, lying flat (2026-09-16, the user's layout pass):** `central/HostedSwapPill.svelte` draws `SwapControl orientation="horizontal"` — one touch row, back on its left half and onward on its right, no inset of its own — above a group of the view's controls, and while it is mounted it holds a claim on `central/swapHost.svelte.ts` (a context `CentralDisplay` provides), so the column is not drawn. Placed so far: the Instrument Rack's pitch/mod wheels (moved to the LEFT of the macros), Omnisphere's ORB (moved left of the pads), Drift's oscillator card, Operator's envelope (through `EnvelopeGroup`'s `header` snippet, inside the trailing hairline), Meld's Macro pad, Wavetable's OSC 1 pad, the single Sampler's Gain · Trnsp · Spread (its view's own grid, the Sampler kit's cells, 2026-09-27), the single Simpler's left-hand column (over Classic/Slice, so Loop keeps its row), and every Drum Rack with its pads showing — a DrumCell, Sampler or Simpler kit's pads + Gain + Trnsp + the kit's third slider (Start on DrumCell, Spread on Sampler, none on Simpler), and on every other kit and an effect's pane the pads alone (`.vm-pads-stack`; the pill adds no width, so a one-column kit's pill is 68px). A flat pill under 6.5rem wide draws its two arrows and no name (a container query), since the name's padding alone is wider than that. The Drum Rack's three lay out on one CSS grid with ONE column set (`.vm-lead-grid`, `data-vm-lead`; since 2026-09-27, so Gain, Trnsp and Filter sit on the same pixels whichever kit is loaded — the user's muscle-memory call): each row NAMES its cells (`grid-area` in `DrumCellControlsRow` / `SamplerControlsRow` / `SimplerControlsRow`) and the view's template places them — DrumCell pads · Gain · Trnsp · Start · FX over its type grid · Time over Filter; Sampler the same cells with Spread for Start, Osc over Pitch for FX and the Amp Envelope's A and R for Time; Simpler with its Time pad across Start, FX and Time — pad `2fr` and slider `1fr`, so the one-ruler rule survives the pill's edge; the pill row and its gap collapse when there is nothing to show. **The pill's name is the door to the browser (ADR-442)** — drawn as a button over the two halves whenever the pill's model carries an `open` (`swapHost`'s `SwapPill.open`, so it follows the pill into every hosting view with no per-view work), exactly as long as the text and as thick as the pill, so a tap ON the name opens the browser and a tap either side of it lands on a half and steps. The pill steps to the neighbor; the name goes and picks one — `useInstrumentSwap.open` pinned to the track with its recorded patch (so it lands on that patch's catalog folder, ADR-441), `useClipSwap.open` pinned to the focused clip's slot. The name never runs closer than `--height-touch` to either end, so each step keeps a 44px target however long the name; a longer one ellipsizes. It is a **tap**: it came from `ClipCentralView`'s column-9 Replace Inst, whose 800ms hold was a gate against a dense rail of clip controls rather than against its own consequence, and opening a browser is neither destructive nor irreversible. It **stays live while the halves are disabled** — "No preset recorded", the AX helper down, a kit Live cannot rank are all names that should open the browser, since it is the way out. A held pad cannot narrow it: the pill steps that pad's similar sounds, the name still replaces the whole instrument, because the pin is a track path. A flat pill too narrow to draw its name (under 6.5rem, over a one-column kit) has no door. (The same day it was first a hot-swap square beside the pill, then a ring icon with no box, before the user moved the door onto the name.) **A view can also hide the pill:** the Pattern Rack calls `claimSwapHost()` in its own script and draws nothing, so its pattern buttons take the whole band (2026-09-17, the user's call). **Everything else keeps the column** — Collision, Electric, Komplete Kontrol and the default view, a Simpler / nested-rack / pitch-only / plugin kit with PADS off, and the audio clip view — because nothing there mounts the hosted pill; a view that places it on one profile gets the column back on the others with no code. `central/useInstrumentSwap.svelte.ts` decides what it steps (`drumSwapKind`, 2026-09-27, the user's call): every instrument, a Drum Rack KIT included, steps folder-next from the track's recorded preset (`services/presetSwap.svelte.ts`), disabled while the track records none; the one exception is a held or latched Drum Sampler (`DrumCell`) pad, a Move hold included, which steps Live's own similar samples for that pad through the bridge and the AX helper (`services/similarSwap.svelte.ts`), disabled with the helper's named state (`ax-helper-down`, `ax-untrusted`) in place of the name while it is not ready. A held pad of any other class steps the kit's folder, since the bridge refuses a single-pad swap on anything but a Drum Sampler. (Until then a kit stepped Live's kit-wide similar-sound buttons, and only a Drum Rack of Samplers — whose multisample pads Live's swap cannot step — its folder.) A failed swap puts its error code where the name was, and the pill dims while a swap works — on a kit the name is the rack's, which a swap does not change. What the pill says is `describeSimilar` / `describePreset`, pure and tested. **The clip view carries the pill too, for an audio clip (ADR-440):** `central/useClipSwap.svelte.ts` names the focused clip's file and steps it through the files Live's own index ranks nearest (`services/clipSimilarSwap.svelte.ts`) — replaced in its slot, relaunched if it was playing, refocused — while a MIDI clip draws no pill and a clip Live cannot rank names why in place of the name (`describeClipSwap`). A step deletes the focused clip, which empties Live's clip view for a moment, so the pill holds the stepping clip until the refocus lands. `CentralDisplay` mounts whichever of the two hooks has a model. `viewRegistry.ts` maps device types to view components. `views/` has 40+ device views. **The Drum Rack is one view for every `DrumGroupDevice` (ADR-428, Milestone 1b):** `views/DrumRackCentralView.svelte` reads the surface's `vm.members` census and picks its own profile by the dominant pad class — the seven virtual-macro controls for DrumCell kits (`full`), a card naming the pad class ("Simpler" / "Sampler", Multisample Mode Simplers included under "Simpler") plus the Trnsp slider for any other native class (`pitch-only`), **the Simpler row for Simpler kits** (`simpler`, 2026-09-07: `views/SimplerControlsRow.svelte` — the Time pad as `attack` × `release`, Attack across and Release up, beside a slider-width Trnsp; enough for now, user's decision — and **`views/SimplerCentralView.svelte` now resolves its parameters by NAME with the index table as fallback**, because the Acuff kit's Simplers list Ve Attack at 21 and Ve Release at 24, not 26 / 29, and its Pitch slider is ±48), **the Sampler row for Sampler kits** (`sampler`, 2026-09-07: `views/SamplerControlsRow.svelte` — Osc and Pitch-envelope XY pads, then the **amp envelope as four sliders in ADSR order inside an `EnvelopeCard`** (2026-09-12, user's call: "can we instead just use 4 sliders for attack, decay, sustain, release?" and "card label should say something like amp envelope and maybe the sliders only need to say A, D, S, R"), then Spread and Trnsp — **on a kit, Decay and Sustain are hidden** via the row's `hidden` prop (user's call, 2026-09-08, the Abbey Road kits), so the bracket holds A and R there and the single-Sampler view keeps all four. The envelope was a Time XY pad (Attack across, Release up) with Decay and Sustain as two separate sliders further along the row — one envelope split across two idioms and read out of order. Four sliders costs a gesture (the pad set two stages with one finger, which on a performance surface is a real loss) and buys the whole envelope in one place. **The bracket is load-bearing, not decoration:** four bare sliders in a row of other bare sliders said nothing about where the envelope stopped and Spread began, and it is the bracket carrying the name that lets each slider be one letter. It was a bordered card until ADR-433 (2026-09-13) and is now two `SectionDivider` hairlines with the name centered above the stages. `attack`/`release` are now their own `SamplerRowSlot`s — the combined `time` slot is gone — which also splits a reading the pad could not make: the Autumn kit's Release macro holds Release and only Release, which the pad could only report as a shared "32/64 macro" badge over both stages — slots tagged `[data-vm-function="oscAmount|oscCoarse"]` etc. — every control a `vm.*` function fanned out to each pad's Sampler by name; no wheels on a kit. **`views/SamplerCentralView.svelte` draws the same row for a single Sampler by parameter NAME** through `selectedTrackStore.paramRange`, writing a section's switch with its amount, plus its own Gain (`Volume`) and Filter pad (`F On` / `Filter Freq` / `Filter Res`, the switch only ever turned on) on the Sampler kit's cells since 2026-09-27, with the wheels beside it — its index-based Time pad (59 / 66) is gone), **one control per pad-rack macro name for a kit of nested Instrument Racks** (`rack-macros`, 2026-09-07: the census's `macros` list rendered one slider per name, each writing `vm.macro.<name>` as `t`, subscribed per kit from the census and released when the names change; Trnsp stands in the transpose macro's place when the census names one as `pitchMacro` — the same knob in semitones, `[data-vm-function="pitch"]` — and is absent otherwise; a name only some pads carry wears a "20/32 pads" badge top-left, `.vm-coverage-badge`), or `views/DrumRackMacroGrid.svelte` (the old `DrumRackKompleteKontrolCentralView`, now mounted by the view rather than the registry, so it deliberately drops the `*CentralView` suffix the reachability test enforces) — one slider per mapped macro of the rack's own, and nothing else — for any rack whose own macros are mapped (the census's `mappedMacros`, Live's `macros_mapped`, never read off names, 2026-09-29) and for plugin-hosted pads. Within the controls a function the kit has no member for is `.vm-slot.vm-none` (ghost dim, `pointer-events: none`) and one every member of which is macro-held is `.vm-slot.vm-held` (ink and value kept, inert, a small "macro" badge); one with only SOME members held stays live and wears the badge with the count ("31/32 macro" — the mapped Jazz kit, whose Transpose macro leaves its Sampler pad free); no census yet renders exactly as Milestone 1. The decisions are pure functions in `$lib/services/drumVirtualMacros.ts`, shared with the FX-grid Pitch slider and the clip view's ±12 buttons. **Beside the controls on every profile sits `views/DrumPadGrid.svelte` — the pads in play** from the census's `pads`: the playing clip's, Live's selected pad, and any pad a finger is holding, and nothing else (2026-09-09, `padGridNotes`). They **stack**: up to four down one column, a fifth starting a second column rather than rebalancing the first, so five reads 4 + 1 and nine 4 + 4 + 1 (`padGridShape`). Past three columns the width would eat the controls, so beyond twelve the rows grow instead. **Each column reads bottom-up** — lowest note at the foot, pitch climbing as the eye does, the way a rack reads (the first cut had it upside down; user, 2026-09-09). `padGridCell` places every tile explicitly rather than leaning on `grid-auto-flow: column`, because an auto flow fills each column from row 1 down and would leave a lone fifth pad at the TOP of its column, out of line with the lowest note beside it; DOM order stays ascending (the screen-reader reading order, and what the tests assert). The column is exactly as wide as its columns need — `--pad-col-w` 68px, so 68 / 140 / 212px — and the controls take the rest; the rows are uncapped `1fr`, so one pad on its own is one full-height tile. **This replaced Live's own pad view** (four columns of consecutive notes, lowest bottom-left, sixteen a page with two `.pad-pager` arrows, the page following the selection) — sixteen tiles was "too small and cluttered" and mostly pads nothing was doing anything with (user, 2026-09-09). **What went with the paging: reaching an arbitrary pad from the interface.** A pad the clip does not play and Live has not selected is not drawn, so per-pad editing is a while-something-plays gesture plus whatever Live has selected; the way to any other pad is Live's own rack, and the grid follows. With nothing playing the grid is one tile. (**Labels are decided for the kit at once** by `padTileLabels` — the leading words every pad shares are dropped ("Chase Kick" → Kick), a leading kit code is skipped ("606 Kick" → Kick), a kit-maker's trailing colon goes ("Kick:" → Kick), colliding labels take one more word while it fits ("Hat Cl" / "Hat Ped" / "Hat Op"; `PAD_LABEL_MAX` 16 — **the label wraps to two lines** rather than clipping, user's call 2026-09-08 after "TOM: Tom 1" showed as "TOM: To"), and a kit whose every chain has the same name shows NO label — color and position say which (user, 2026-09-08: sixteen tiles all reading "Chase" said nothing; note names as the fallback were built and hidden at his request, `noteName` kept for when they return); over the WHOLE kit, not the pads on screen, so a tile does not rename itself when a clip changes which of its neighbors are drawn.) **The grid is switchable from the Sections card's PADS row** (`uiPrefsStore.showDrumPads`, default on, 2026-09-08): off, the column goes back to the controls and this view is what it was before the grid landed — full-width controls moving the whole kit. The view clears `drumPadScope` on that edge, since a hold left standing would scope every writer (the FX grid's Pitch slider included) to a pad no longer on screen. **While a pad is held the controls wear ITS color** (2026-09-09): the chain color Live gave the pad, the one its tile is filled with, taken through `trackInk` — the same L 0.66–0.80 / C 0.11–0.19 envelope the track's own color goes through, because a chain color is any of Live's 70 and some are far too dark to draw a slider's line with (the tile keeps the raw fill; a fill with contrasting text has no such problem). Nothing held, or a pad Live left uncoloured, and they are the track's again. Three things deliberately do NOT follow — color follows scope: the **pad grid** keeps `drumRackInk`, since its `--pad-ink` paints the pads Live left uncoloured and handing it the held pad's color would make every one of those look like it shared it; and the **Drum Buss** (the grid tile and its view since ADR-431; a `CentralDisplay` rail before) keeps its own drum-family ink, which is right — those are track-level devices, not per-pad, and a hold does not scope them (user, 2026-09-09). Same reasoning leaves `DrumRackMacroGrid` alone: `profileFunctions('macro-grid')` is empty, so a hold scopes nothing there either. **A tap LATCHES, a hold is momentary (2026-09-09)** — the same split Solo and mute make, sharing their `shouldRestoreOnRelease` / `MOMENTARY_HOLD_MS` rather than growing a second threshold. **A track change clears every scope (2026-09-11, user's call):** navigate to another track and every latch and hold goes, on every rack, so a track is always arrived at unscoped — including one you latched a pad on and are coming back to. **A pad held on the Move is a hold here too (ADR-432, 2026-09-11):** the Max Utility patch times it, the surface names the pad Live selected, and it lands on `drumPadScope` as an external hold — the tile lights, the controls take the pad, the FX grid scopes — and lifts as a momentary release, never a latch. Tap a pad and the controls stay its with nothing on the glass; tap it again to let go, or tap another to move the latch (one at a time). Hold and it is what it always was. A latched pad wears the same held treatment and lends the controls its color, because the state is identical — only how it got there differs — and holding a pad over a latched one scopes the finger's pad, returning to the latch on release. The tile reports WHY a press ended (`up` / `cancel`), so a browser-claimed gesture or an unmount under the finger cannot leave a latch nobody asked for. **Hold scopes, lift returns:** nothing held → the controls move the kit as before; touch-down on a tile selects the pad in Live (`vm.selectedPad`, framed in the ink; Live → iPad syncs through the rack view's listener), scopes the view (`data-vm-scope`, the tile a solid block) and the controls read that pad's own values (`vm.pad.<note>.<fn>`, subscribed for Live's selected pad and every held pad, for the functions `profileFunctions(profile)` draws) — a drag writes the pad's row through `writeFn` → `writePad`, never the kit row, and a lift returns everything to the kit. Several held: the control shows the LAST pressed (= Live's selection), the others move by the same delta from their own values (`padLocal` remembers what we last wrote each held pad, so the delta never chases an echo); an enum (FX type) lands on every held pad as is; a held pad whose row reads nil ghosts that control while held. Selection state is the interface's, never the surface's, so two clients cannot fight over it — and since the layout pass (2026-09-08) it lives in **`stores/v6/drumPadScope.svelte.ts`** (pointer id → note, press order, per device, plus the one scoped-write rule `writeScoped`) rather than the view, because **the FX grid's Pitch slider (`device-panel/InstrumentControl.svelte`, `drum-pitch`) is the kit's one pitch knob and obeys the same hold from its own tree**: while a pad is held it shows that pad's pitch and writes `vm.pad.<note>.pitch`. **The central Trnsp is always drawn on a DrumCell kit** (2026-09-12, user's call) — from 2026-09-08 it was hidden while `uiPrefsStore.showFxGrid` was on, since the grid's Pitch slider is the same knob, which left the kit's pitch missing from its own view by default; both read and write `vm.pitch` and obey the same hold, so showing both costs nothing. **The FX type is a 3×3 of buttons under the FX pad** (2026-10-04, user's layout; `.fx-type-option`, one `use:press` each), and the FX pad is titled with the chosen type; a choice writes through the scope rule, so with a pad held it is that pad's type. On a DrumCell kit the **Time pad stacks over the Filter pad** in the next column (the row takes the view's `filterSlot` as its `filter` snippet), each column two equal halves so the type grid sits level with Filter; the two columns split the three pads' `6fr`, so Gain, Trnsp and Start stay on the other kits' pixels. **A Filter XY pad rides beside it** (2026-09-09, `{#snippet filterSlot()}` + `.vm-filter-col`, the same outside-the-profile-switch placement): cutoff across (`vm.filterFreq`, which carries the filter's own switch as its first member) and resonance up (`vm.filterRes`). Bound by name — `Filter On` / `Filter Freq` / `Filter Res` on a DrumCell, `F On` and the same two on a Simpler and a Sampler. **The switch never follows the floor**: cutoff at the bottom with the filter ON is closed and silent, so switching it off there would open it wide instead and the bottom of the sweep would jump from silence to full. Resonance is not 0..1 everywhere (a Simpler's tops out at 1.25), which costs nothing because the fan-out spans each member's own range. Live's hard red headroom band in the top 6% survives in every skin, so clipping still reads as clipping. Selected strip keeps its track color but draws a thicker/brighter outline + glow (not white, so it never reads as muted). The playhead and the MIDI lanes read the same window. **A stopped clip draws no playhead** (strip, grid cell and editor alike); a clip Live holds as playing while the transport is stopped keeps its line, frozen where Live will resume it — the surface restates that position after every re-send and on the stop. **The strip drops its preview entirely while `sessionMode` is on** — the grid a third below already draws the same clips; the Clip section stays as the select-and-show-Clip-view tap target. ## Conventions

- Touch-optimized for iPad Safari — all interactions must work with touch
- **Input goes through `$lib/actions` (ADR-427).** `use:press` for a
  discrete control, `use:drag` for a continuous one; both own their
  `touch-action` and their own teardown. **Never** `onclick` under
  `tracks/`, `layout/`, `session/`, `clips/` or `controls/` — a performer
  touches those with two hands and iOS synthesizes at most one click per
  gesture — and never `touches[0]`, which is the first finger on the
  glass rather than the one that started your gesture. The gate fails
  the push on either (`touchDialects.test.ts`, via `npm run check:touch`). `central/views/**` is out of
  scope: one-at-a-time device panels, where a click is honest.
  `npm run multitouch` replays concurrent fingers against the real
  components; §13 of the manual test checklist is the iPad half, which
  no harness here can answer
- Writes to Live go through the named commands in `$lib/services/` (`trackCommands`, `clipCommands`, `sessionCommands`, `deviceParams` …), never `$lib/api/simpleClient.ts`: `npm run check:writes` fails on a component that imports it
- The reusable controls are exported, one paragraph each, from `blocks/index.ts`; `docs/reference/blocks.md` is generated from it (`npm run blocks:catalog`)
- **The skin.** There is ONE skin, **Hybrid**, and it is not a choice: `data-skin="hybrid"` (palette token block) and `data-grammar="flat"` (the flat grammar) are hard-coded on `<html>` in `app.html`. Every component with its own chrome carries a `:global([data-grammar="flat"]) …` block at the end of its `<style>` (Tailwind utilities via the `flat:` variant), following the **flat-grammar cookbook** in `docs/reference/ui-architecture.md` §8.1 — flat surfaces, 1px `--line-strong` edges, 2px radii, no glow/wash/shadow, OFF = `--surface-well` field / ON = `--phosphor` + `--flat-on-fg`, `var(--playhead)` / `var(--scrim)` / `var(--edge-light)` / `var(--well-shadow)` instead of literals, titles authored mixed-case. New components need their flat block in the same PR. The retired GRATICULE skin is still the base token layer Hybrid overrides — see Looping's `documentation/archive/graticule-skin.md`.
