# Services - Business Logic

Services contain the core business logic, separated from UI components and state stores.

## Core Services

| Service | Purpose |
|---------|---------|
| `instrumentService.ts` | Identifies instrument types (drumrack, wavetable, omnisphere, etc.) from device info. **Every `DrumGroupDevice` is `drumrack` since ADR-428 Milestone 1b** — the old `drumrack-komplete-kontrol` split read macro names (FX1/FX2 on macros 1–2) and sent every Simpler / Sampler kit to a macro grid that moves nothing on an unmapped rack; the Drum Rack view now picks its mode from the surface's `vm.members` census. |
| `drumVirtualMacros.ts` | The UI-side reading of the Drum Rack's virtual macros (ADR-428, Milestone 1b): the `vm.*` property names, the `vm.members` census parser, and the decisions every consumer shares — **profile** (`kitProfile`: a rack whose own macros are mapped, or plugin-hosted pads → macro grid, one slider per `mappedMacros` entry (2026-09-29); DrumCell-dominant → the full seven controls; Simpler-dominant → `simpler`, the Simpler row (`SimplerControlsRow`: the Time pad as `attack` × `release` and Trnsp — enough for now, user's decision 2026-09-07); any other native class → the kit-class card + Trnsp only; Sampler-dominant → `sampler`, the Sampler row (`SamplerControlsRow`: Osc / Pitch-envelope / Time pads, Decay / Sustain / Spread sliders, Trnsp) drawn from the fixed functions `release`, `sustain`, `oscAmount`, `oscCoarse`, `pitchEnvAmount`, `pitchEnvAttack`, `spread` (Sampler-bound by name; `none` on DrumCell kits) — the same row the single-Sampler view draws from its own parameters by name via `SAMPLER_ROW_PARAM_NAMES` / `SAMPLER_ROW_SECTION_SWITCH` — 2026-09-07; nested-Instrument-Rack-dominant with named macros → `rack-macros`, one control per pad-rack macro name from the census's `macros` list, each `vm.macro.<name>`, laid out by `rackMacroLayout`, one slider per name, with `vmMacroState` / `vmMacroHeldBadge` / `vmMacroCoverageBadge` ("20/32 pads" for a name only some pads carry); the census's `pitchMacro` names the transpose macro `pitch` binds through, which `rackMacroLayout` leaves out of the row so Trnsp stands in its place — 2026-09-07; from the census histogram, never macro names), **state** per function (`live` / `held` = every member macro-held, read-only / `none` = no member, dimmed / `unknown` = no census yet, renders as Milestone 1), and **writability**. Used by `DrumRackCentralView`, the FX-grid `InstrumentControl` and `clipTranspose`. No name-based macro fallback for a held function, by decision. **`gain` (2026-09-08)** is on every profile but the macro grid: `Volume` on DrumCell / Simpler / Sampler pads (through each one's own range) and, on a nested-rack kit, each pad's own chain volume — so the Drum Rack view draws one Gain slider in the same place whatever the kit is, ghosted where the kit binds nothing (an Operator kit). **`filterFreq` / `filterRes` (2026-09-09)** are the filter as one XY pad on the same profiles, cutoff across and resonance up, with the filter's own switch as `filterFreq`'s first member — and that switch never follows the floor back off, because cutoff at the bottom with the filter ON is silence and switching it off there would open it wide. **It also owns the PAD GRID's decisions** (2026-09-08/09): `clipPadNotes` (the playing clip's distinct pitches) and `notesCrossed` (which of them the 30 Hz playhead just passed, loop-aware); `padGridNotes` (the pads in play — clip, selection and holds as equals); `padGridShape` (stack four down a column, then start a second; beyond twelve grow rows rather than out-widen the controls) and `padGridCell` (each column placed bottom-up, lowest note at the foot — explicit placement, because an auto column flow puts a lone fifth pad at the top of its column); `padGridSlots`, `padTileLabels`, `padColorCss` / `padTextCss`. The paged-grid helpers `padPages` / `padPageIndex` and the `compactPad*` trio were deleted with the paged view on 2026-09-09. |
| `clipTranspose.ts` | Pitch shifting by track / instrument type. **Drum Racks go through `vm.pitch`** (every native pad type, mapped or unmapped; refused with a warning when the census says pitch is held or absent, or before the cold read) and are **never note-shifted** (+12 on a kit triggers other pads); **Instrument racks ask the surface first** (`/looping/v3/track/transpose`, 2026-09-25): it finds a Drum Rack wrapped inside the rack by class, as Permute's pitch route does, and moves that kit's `vm.pitch` — the UI cannot address a device inside a rack chain. Only a `not-drum` answer (or none within 1 s) falls through to the name-based macro scan (`findTransposeParameter`) and then the note shift; a `held` kit gets the named macro but never the notes. Audio clips keep `pitch_coarse`. |
| `clipOperations.ts` | Clip recording, looping, timing operations. Also owns the **auto-trim** flow (`armAutoStartMarker`) — both capture-to-Simpler and convert-clip-to-Simpler call it after firing `replace_sample*` to set Simpler's start position to the first detected transient. See ADR-354. Auto-trim writes Simpler **param 3 (Sample Start)** and explicitly resets `sample.start_marker` to 0 — Classic-mode brace reads param 3, not start_marker. **Both flows resolve off the surface's `/looping/v3/simpler/replaced` ack (2026-09-17)**, which names the Simpler's devicePath and the sample's absolute path, and then hold their own `sample.length` / `sample.start_marker` subscriptions — so neither the trim nor the Recent entry depends on a view being mounted on that track. They used to infer both halves from `sample.file_path` property echoes, accepting the first from a devicePath that hadn't existed at arm time; the convert flow's adjacent track insert shifts existing devices onto that path, so the guess discarded the echo it was waiting for on every convert but one on the last track. The capture flow keeps the echo as an exact-path fallback for a dropped ack; the convert flow has no key to match on and waits for its ack. Convert also adds to Recent **optimistically** on the tap, from `clipSampleService`'s cached path — `replace-sample-failed` prunes it (see `v3Handshake`'s error routing). |
| `trackPreparation.ts` | Atomic track create-or-reuse + load via `/looping/v3/track/prepare_for_preset`. Per-trackType single-flight queue, request_id correlation. |
| `trackOperations.ts` | The **Dup Trk** variation gesture — `duplicateTrackAndReset`. Fires `/looping/v3/track/duplicate [request_id, sourceTrackPath, clear_clips=1]`, then resets the copied Permute to defaults once the new track's state echo lands. **Emptying the copy's clips is the surface's job, not this file's** (2026-09-04): a duplicate re-indexes every track below the source, so until the next `state/full` the UI's record at `tracks/<N+1>` still describes the *displaced* neighbor — deleting "this track's clips" off that snapshot cleared the wrong scenes, typically leaving all but one. The same staleness is why `waitForNewTrackReady` now waits for `v3Store.tracks.size` to exceed the pre-duplicate count before it trusts a record at that path: the neighbor's record answers a `.get()` instantly and usually carries a Permute of its own, so reading the chain off it aimed the param reset at whatever device sat at that index. A missing Permute or a lapsed poll degrades to a warning — the duplicate and its emptying already succeeded server-side. Also `commitGroupGesture(members)` — the Group button's one wire call (`/looping/v3/track/group`, `groupGestureStore`'s `commit()`), sent once per gesture with the whole anchor-plus-taps member list as a JSON arg; everything before that is local (see `stores/v6/CLAUDE.md`). |
| `deviceMoveService.ts` | Moving/reordering devices on a track's device chain |
| `trackColoring.ts` | Auto-color on preset load (ADR-399) **and, since protocol 3.7.0, auto-role**. A load says where it came from (`AutoColorSource`): a preset from a browser Place passes its Place's role (`placeRole`, `Preset.role`, which Recent also stamps on an entry whose file lies in a Place) and that is the answer outright for both color and role — `null` = a Place with no role, which colors and records nothing; a sample or clip picked in a Place passes `audio: true`, the audio color and no role. Only a load with no Place behind it (a Recent entry outside every Place) reads its path (`$lib/utils/presetPath.presetCategory`: the category folder, else the deepest folder naming one). `resolveAutoRole` returns the role and `applyAutoRoleOnPrepareAck` sends `/looping/v3/track/set_role` beside the color write so Live persists it in the Set. **`null` means "this load says nothing about the rail"** and the caller leaves any existing role alone — a wrong role would be believed outright since the reconstruction tiers were deleted. The brand fallback (Ableton yellow for an unrecognised `<Brand>/<Type>/…` path) and the browsed-rail fallback went with the type catalogs at the cutover (2026-09-24): no load can reach them. |
| `trackCommands.ts` | UI-initiated track-metadata writes (`setTrackVolume`, `setMasterVolume`, `setTrackName`, `setTrackMute`, `setTrackSolo`, `setTrackFoldState`). `setTrackFoldState` (ADR-410) folds/unfolds a Group Track via `/looping/v3/track/set/fold_state`; it goes through `applyTrackFoldState` rather than `applyTrackMetadata` because `foldState` isn't a table-driven metadata attr on either side — the LOM has no fold listener at all. Each pairs `applyTrackMetadata` / `applyMasterMetadata` with the matching OSC `send` so the v3 store reflects what the UI just sent without waiting for the surface's (suppressed) listener echo. Components call these instead of `send` directly for value writes — see ADR-358 and `docs/reference/wire-protocol.md` §4.4. |
| `clipWaveformService.ts` | Single entry point for `/api/sample-peaks` waveform fetches (ADR-360). LRU cache keyed by `(filePath, bins)`, AbortController per inflight slot, dedupes concurrent requests. Consumers: **`ClipPreview`** — the shared renderer behind both the track strip (bins=256, via `TrackClipView`) and every session-grid cell (bins=64, via `SlotCell`, ADR-415) — plus `SimplerLoopControl` (Simpler view at bins=1024). `TrackClipView` no longer calls `getPeaks` itself; drawing moved into `ClipPreview`. Single audit point for the Vite prod-path trap on `/api/sample-peaks`. **The key includes `bins`, so a strip and the grid cell below it are two entries for the same file** — `CACHE_MAX` is sized for the grid's whole working set (`visibleTracks × (visibleRows + 1)` at both bin counts), not for one waveform per strip. The route itself runs **Path A** (streaming PCM peaks for WAV/AIFF/AIFC, no size cap) or **Path B** (full-decode for compressed mp3/flac/ogg, gated by `paths.waveformMaxBytes`); see ADR-362. `getPeaks(path, bins, { force: true })` bypasses the cache + aborts any inflight fetch for the same key — used by `ClipPreview` to re-fetch when an in-progress recording's `lengthBeats` finalizes (ADR-363). |
| `clipNotesService.ts` | MIDI clip notes pull endpoint (ADR-360) — the **cheap, identity-blind** blob for strip thumbnails. `requestNotes(clipPath)` → resolves with `MidiNote[]`, rejects on 5 s timeout. Decodes the surface's float32 blob (`<ffff` × n) via `DataView`; a negative velocity is a muted note (ADR-444) — folded into `MidiNote.muted`, velocity handed on as `abs()`, `-0` caught with `Object.is`. `subscribeNotesChanged(clipPath, cb)` re-fetches when `/looping/v3/clip/notes/changed` fires (shared by the rich channel too). **Caches resolved notes by clipPath** (ADR-415) — the session grid remounts a MIDI cell on every scene-window row, so in-flight dedupe alone meant a drag re-pulled every visible clip's blob; `handleClipNotesChanged` drops the entry before fanning out to subscribers, and `bridge-resync` clears the map. `clip-not-midi` and `clip-not-found` resolve with `[]` (UI shows ghost); other typed errors reject. Owns `toUint8Array` (bridge Buffer-shape blob normaliser), reused by the rich service. |
| `clipSampleService.ts` | **ADR-415.** Pull endpoint for "what sample is in this slot?" — `clip/sample/get [requestId, clipPath]` → `clip/sample [requestId, clipPath, isAudioClip, filePath]`, handled by Python's `ClipsComponent`. Exists because the session clip grid draws a waveform in cells that aren't playing, and nothing else on the wire carries a path for a non-playing slot: `track/playing_slot` rides ONE `playing_slot_index` listener per track, `clip/property` is focus-only, and `state/full`'s C record omits `file_path` (a path per clip would add kilobytes of strings to a bundle that already chunks). Deliberately mirrors `clipNotesService` — same requestId plumbing, same single-flight-per-clipPath — since the two are the audio and MIDI halves of one per-cell question. **Additionally caches resolved answers by clipPath** (`peekSample` reads it synchronously so a re-scrolled cell paints on the first frame), cleared on `bridge-resync`. A MIDI clip and an audio clip with an empty path are both *replies*, not errors. |
| `clipRichNotesService.ts` | **Rich, identity-carrying** focused-clip note channel for the central editor (clip-view-mirror M3/M4, ADR-382). `requestRichNotes(clipPath)` issues `notes/rich/get`, reassembles the chunked begin→chunk→end sequence, verifies the FNV-1a checksum (re-rejects on mismatch / missing chunk), and decodes the `<iffffi>` struct (24 B/note, `noteId` int32 + extended fields) into `RichNote[]`. M4 edit senders: `sendRemoveNotes` / `sendModifyNotes` / `sendAddNotes` (the last resolves with Live's assigned ids off `notes/added` for temp-id swap). **Own-write echo suppression** (`markLocalWrite` / `shouldSuppressReconcile`, ~400 ms window) so the editing client doesn't reconcile against its own optimistic edit. `encodeRichSpecs` / `computeRichBlobChecksum` mirror the surface byte-for-byte. |
| `presetSwap.svelte.ts` | **Folder-next (ADR-439 phase 2)** — the swap pill on every instrument, a Drum Rack kit included (`useInstrumentSwap`'s `drumSwapKind`, 2026-09-27); only a held Drum Sampler pad steps similar samples instead. Steps from the track's recorded preset (`TrackRecord.preset`, protocol 3.9.0 — `''` once the track's instrument is no longer the one that load left, Live's undo or a hot-swap, and the pill then cannot step) to its neighbor in the catalog folder and loads it with `loadPresetWithVariant(…, trackPath)` — replace-instrument mode, clips / Permute / FX kept. Wraps at the folder ends; one load at a time per track. The folder follows the recorded preset, except for the record the pill's own load produces, which is recognized and looked up no further, and a slower catalog lookup never overwrites a newer one (a per-track token). No Commit or Return since the pill (user's call, 2026-09-15): the way back is the other half, or the browser. A refusal is transient (`swapErrors`). |
| `presetSwapCatalog.ts` | Where a recorded preset sits in its Place's folder (the Places since the browser-places cutover). The recorded path is read through the Places index's **alias map** first (a record from before the Places names a file in the old vendor tree, still in saved Sets), then the Place whose folder holds the path, then the leaf whose items hold that exact `fullPath` (`PlacesAdapter.findPresetSiblings`, reaching into the Place's Samples file for a path under it). `typeId` is the Place's rail id (`place:<id>`), and the list keeps only what a step can load (installed plug-ins; instrument or kit kinds). A path no Place holds fetches no Place file at all and answers null — the old sweep across every catalog (14 files, 19.2 MB) is structurally impossible. One adapter per Place for the session, so a multi-MB catalog is fetched once. Since ADR-441 the answer also carries the **folder path** to that leaf — the browser's own `currentPath`, which is what lets a Replace Inst hold open on the track's patch instead of wherever the last browse ended. |
| `similarSwap.svelte.ts` | **Pad swap (ADR-439 phase 3)** — the swap pill on a held or latched Drum Sampler pad (the UI no longer sends the `kit` scope since 2026-09-27; the bridge still takes it). Sends `/looping/v3/drum/swap_similar` and settles on its own request id's reply; keeps whether a swap is in flight and its named error per rack and scope (`kit` / `pad:<note>`). The bridge does the work through the AX helper — see `interface/bridge/CLAUDE.md`. **A refusal is transient** (`swapErrors`, below). |
| `swapErrors.ts` | **How long a refused swap wears its reason** (2026-09-15). All three swap stores keep state in a map keyed by path, and nothing used to clear an error but a later *successful* step on the same key — so a pill went on saying `ax-control-disabled` about a kit that had become perfectly swappable, and because the keys are positional, deleting a track above a rack handed a different rack the previous one's failure as its label. `holdSwapError(key, clear)` shows it for `SWAP_ERROR_TTL_MS` (6 s) and then runs the store's own closure; `dropSwapError` cancels when the key moves on under its own steam; a `bridge-resync` flushes every held reason at once, the contract `clipSampleService` / `playingClipsStore` / `sceneWindowStore` follow. The module owns only the timing — each store keeps the shape of its own state. |
| `clipSimilarSwap.svelte.ts` | **Similar sounds for an audio clip (ADR-440)** — the swap pill on the clip view, where Live has no swap of its own. Asks `/api/similar-samples` once per file for the files Live's index ranks nearest (audio files only; a `Type|Loop` file meets loops, a `Type|One Shot` one one-shots) and steps through the clip's file and then up to 50 neighbors, wrapping at the ends. **A step is one request**, `/looping/v3/clip/swap_file [requestId, clipPath, filePath]`, and Live does the swap inside one undo step — the old clip's settings, a name of its own, its playing and its focus onto the new clip, and the old file put back when the new one will not load (`ClipsComponent.handle_swap_file`; see `surface/CLAUDE.md`). The step settles on the reply carrying its request id (15 s), and the pill moves to the new file only on `ok`. The list follows the clip's file, except for the file its own step loads; a clip Live cannot rank carries a named reason (`not-indexed`, `no-vector`, `no-similar`, `no-file`, the route's `no-database`, and its `forbidden` for a file outside the sample roots — `$lib/server/sampleRoots`), shown transiently (`swapErrors`). |

## Coordinators (Svelte 5 Runes)

| Coordinator | Purpose |
|-------------|---------|
| `instrumentDisplayCoordinator.svelte.ts` | Syncs instrument selection with central display UI. Two one-shot flags steer it, and the newest one wins: `suppressAutoViewSwitch()` (an explicit view choice — the mini-sequencer tap) holds the current view for the next device-list update, and `requestInstrumentView()` forces the instrument view onto the update that carries a new instrument. The browser's `presetLoader` arms the latter **before** the load goes out, because the plain auto-switch only fires on a *new* track and a load lands in two updates — track first, device list second — so a load that reused the selected track (replace mode, or Python reusing an empty track you were already on) used to leave you on the clip/system/device view you came from. The request is peeked, not consumed, on the intermediate empty-device update (and suppresses its clip-view flash), retired on an audio track or the master, and expires after 15s so a failed load can't hijack a later selection. |
| `clipDisplayCoordinator.svelte.ts` | Syncs clip state with visualization components |

## Adapters (`adapters/`)

Preset browser adapters - each implements a different browsing strategy:

| Adapter | Purpose |
|---------|---------|
| `browserAdapter.ts` | Base interface all adapters implement, and the `Preset` / `FolderNode` shapes |
| `recentInstrumentsAdapter.ts` | Recently used instruments and samples for quick access. `recentThroughAliases` reads each entry through the Places alias map (an entry recorded in the old vendor tree loads and shows as its Sidebar copy, and the two are one item) and gives an entry with no recorded role the role of the Place its file lands in |
| `placesAdapter.ts` | **The Places** (browser-places plan): `place:<id>` vendorIds over `/api/places/<id>.json`, built at runtime by the Mac's Places service (`$lib/server/places/service.ts`) for the Places ticked in Settings. `placesLive.ts` holds the server-sent event stream that says when the catalog changed; the browser then re-reads the rail and the level on screen, keeping every button's folder position (`browserNavigationStore.refreshVendorStates`). A Place's `Samples` folder is an `external` stub filled from `<id>-samples.json` the first time it is opened. `setKindFilter` narrows folders by their `kinds` counts (no descent) and items by their own `kind` — the browse switch's two halves. Every item is stamped with its Place's `role` for coloring. `findPresetSiblings` reaches into the Samples file for a path under it. `getPlacesIndex` memoizes the index (a failed fetch is not memoized) |
| `index.ts` | Adapter registry: `getAdapter` answers Recent or a Place, and throws for anything else. The type-first, audio-clips and vendor (`unified`) adapters were deleted at the cutover (2026-09-24) |

## Conventions

- Services are pure functions or singleton objects (no Svelte dependency except coordinators)
- Coordinators use `.svelte.ts` extension for runes
- All OSC calls go through `simpleClient.ts`
- Tests in `interface/src/__tests__/unit/services/`

## Device view routing and the pad scope (issue #491, 2026-09-10)

- `deviceViewRouter.svelte.ts` — **the one place "open this effect's
  view" goes.** Sixteen tile call sites used to swap the central display
  directly; now `BaseDeviceControl` hands them `openView()` and every
  frame of a drag may call it. With nothing scoped it is the top-level
  device view as before (and a no-op when already up). While a pad is
  held or latched on the selected track's Drum Rack it sets the Drum
  Rack view's **pane** (`drumPadScope.setPane`) — a top-level swap would
  unmount the pad column, cancel the held pointer and snap the grid back
  to the track mid-gesture — and brings the Drum Rack view back first if
  another view is up, because a pane nobody can see is no answer.
  `activeDrumRackScope()` is the reactive "is a pad scoped on the
  selected track's Drum Rack, and which" that the FX grid provides as
  the tiles' `fxScope` context.
- `drumVirtualMacros/` is a **directory** since E0 of the same issue
  (`wire` / `profiles` / `padLabels` / `padGrid` / `padFx`), still one
  import path. `padFx.ts` parses the surface's `vm.padFx` presence row
  and builds the stand-in device records a pad's tile reads active from
  before the pad's own bundle lands (`padDeviceStubs`);
  `profileForPadClass` in `profiles.ts` is the row a held pad earns on
  its own class (the Jazz kit's Sampler pad gets the Sampler row).
