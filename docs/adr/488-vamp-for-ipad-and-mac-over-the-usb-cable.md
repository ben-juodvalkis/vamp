# ADR-488: Vamp for iPad and Vamp for Mac, over the USB Cable

## Status
**Proposed** (2026-10-27), on branch `bj/native-ipad-app`. Accepted once it
has run on the rig's iPad. Issue #8. No Live restart: the bridge, the
interface server and the menu-bar app only.

## Context
The iPad reaches Vamp as a Safari page. On 2026-10-27 that stopped being
dependable, and every cause was the network the page needs to find the Mac:

- macOS now keeps the iPad's USB network interface private
  (`HiddenConfiguration` / `HiddenInterface` in
  `/Library/Preferences/SystemConfiguration/NetworkInterfaces.plist`). It
  appears in neither System Settings nor `networksetup`, so it cannot have
  the fixed `192.168.100.1` the page used to be saved at; it self-assigns a
  `169.254.x.x` address instead. Resetting the iPad's trust did not change
  that.
- That link reset twice in 90 s while presets loaded (down 20–30 s, a new
  address each time), and after a replug it took 20 s to get an address at
  all.
- The Mac had renamed itself after name clashes (`looping-studio` →
  `-2` → `-3`), so a saved `.local` URL is only as stable as the name.

Measured the same night, usbmux (Apple's device channel over the cable, the
one Finder and Xcode use) was attached and carrying a connection 2 s after
a replug, 18 s before the network link had an address. A Safari page cannot
use usbmux; an app on the iPad can, which is how Duet, Luna and TouchOSC's
USB mode stay up.

The page also reached the Mac on two ports, the page server and the
bridge's 8081, and logged in to the bridge with a proof fetched over the
first and sent on the second.

## Decision
- **One port for the page.** The page dials its own origin at
  `osc.webSocket.path` (`/bridge-socket`); the interface server (`vite dev`
  and `vite preview`) passes the upgrade through to the bridge on 8081, Origin
  intact. Other clients (the menu-bar app, perf and shot scripts) still dial
  8081. The screenshot harness routes the path as well as the port.
- **Two native apps in one Xcode project** (`owner/apps`, generated by
  XcodeGen from `project.yml`, the project committed):
  - **Vamp for iPad** is a full-screen web view of the same interface, not a
    copy of it. It loads `localhost:8889`, where its `LinkServer` parks each
    connection and asks the Mac for a stream. An interface change needs
    `npm run ipad` and a reload, never a new app. It keeps the iPad awake,
    keeps a loaded page up with "Reconnecting to the Mac…" while the Mac is
    gone, and Safari's Web Inspector can attach.
  - **Vamp for Mac** is the menu-bar app (moved from `owner/menubar`, history
    kept) plus the link: it follows the iPad through usbmuxd and keeps a
    `LinkClient` to the app while it is plugged in, splicing each stream to
    the page server Safari uses. `scripts/launch-menubar.sh` builds and starts
    it, under the same `features.menubar` switch.
  - **The link** (`Shared/`): usbmux only lets the Mac connect to the iPad, so
    the iPad listens on loopback port `padLink.devicePort` (47800) and the
    Mac dials one control connection, pinged every 2 s, and one stream per
    `OPEN <id>` the iPad sends on it. One ASCII line says what a connection
    is; a stream is raw bytes after it.
- **Safari stays.** It is the fallback on the rig and the way in for anyone
  without the app; the reconnect hardening of 2026-10-27 (1165a83, 3d0bd82)
  is what keeps it usable.

## Consequences
- A replug costs the app ~2 s instead of ~20 s plus a reconnect; a Mac rename
  or address change costs it nothing. Not yet measured on the iPad itself.
- Measured on this Mac with the app in the iPad Pro 12.9" Simulator
  (`VAMP_LINK_DIRECT=1` links over loopback; `-padLocalPagePort` moves the
  app's page port off the Mac's own 8889): the live set loads through the
  link, and with the Mac app restarted the page's connection is spliced
  through 0.5 s later with no reload.
- Nine XCTests run both ends on the Mac over plain TCP (2 MB binary intact,
  20 connections at once, a page refused at once with no Mac, the link back
  after the Mac side goes). They run in Xcode, not in the gate.
- The bridge sees the page's socket from 127.0.0.1 (the interface server)
  rather than from the iPad; its gone-client ping check still reaches the
  page through the pass-through.
- Installing on an iPad needs Developer Mode, pairing with Xcode and a signing
  team (`owner/apps/Config/Local.xcconfig`, gitignored). Distribution beyond
  the owner's iPad (TestFlight or the App Store) is undecided.
- Later: Vamp for Mac starting and supervising the bridge and page server in
  place of the Terminal and the status page; the USB cable as the trust
  boundary in place of the device pairing `security.plan.md` plans.
